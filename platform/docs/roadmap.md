# برنامهٔ بک‌اند بازی روی SpacetimeDB

تأییدشده در ۱۴۰۵/۰۸/۳۰.

## هدف

کارهایی که روی nakama-farsi ساختیم، روی SpacetimeDB دوباره ساخته شوند، همراه با یک پنل مدیریت تازه و تمیز. خودِ موتور SpacetimeDB را تغییر نمی‌دهیم. همهٔ منطق داخل ماژول‌های TypeScript است.

## ساختار پیشنهادی

```
platform/packages/
  base/         ورود با پیامک، حساب، نقش ادمین، زبان‌ها، دسته و برچسب، برند
  economy/      ارز، متا، جایزه، فروشگاه، پرداخت، هدیه
  gamification/ تسک، اچیومنت، استریک، رویداد، گردونه
  items/        آیتم، اینونتوری، قانون‌های محصول، پیشنهاد ویژه
  publication/  خبر، اعلان، پوش، پیامک گروهی
  social/       دوست، چت، گزارش بازیکن، سهمیهٔ پیام
platform/games/
  template/       ماژول یک بازی که بسته‌های بالا را کنار هم می‌گذارد
platform/panel/   پنل مدیریت (React + Vite)
platform/e2e/     تست با Playwright و کلاینت Node
```

هر بازی یک دیتابیس جدا روی همان سرور دارد. بسته‌های مشترک کد را یک جا نگه می‌دارند و هر بازی فقط همان‌هایی را که لازم دارد برمی‌دارد. پنل به هر دیتابیسی که انتخاب شود وصل می‌شود.

## پنل

- **ظاهر:** طراحی Plane، فونت یکان بخ و آیکون‌های Phosphor، مثل کنسول جدید ناکاما. فارسی و راست‌چین، با اعداد فارسی.
- **اتصال:** مستقیم با WebSocket و کدی که `spacetime generate` می‌سازد. جدول‌ها و گزارش‌ها خودشان زنده به‌روز می‌شوند و API جدا لازم نیست.
- **ورود ادمین:** مثل کنسول ناکاما با نام کاربری و رمز. مالک از `ADMIN_USERNAME` و `ADMIN_PASSWORD` در env می‌آید و بقیهٔ کاربرهای پنل را مالک می‌سازد. ورود با پیامک فقط برای بازیکن‌هاست. هر reducer مدیریتی نقش را چک می‌کند.
- **صفحه‌های اول:** ورود، انتخاب بازی، داشبورد، تنظیمات پروژه (برند، زبان، پیامک، درگاه)، بازیکن‌ها.

## ریسک‌هایی که از قبل می‌دانیم

۱. **امکانات unstable:** callback درگاه با HTTP handler و درخواست بیرونی با procedure ساخته می‌شود و هر دو هنوز unstable هستند. نسخهٔ SpacetimeDB را ثابت نگه می‌داریم و قبل از هر ارتقا تست کامل می‌گیریم.
۲. **عدد تصادفی:** `ctx.random` قابل حدس است. برای کد ورود، گردونه و جعبهٔ شانس از HMAC با کلید مخفی استفاده می‌کنیم.
۳. **گزارش‌ها:** SQL آن برای گزارش سنگین ساخته نشده، پس آمار روزانه را هنگام هر رویداد در جدول‌های جمع‌بندی ذخیره می‌کنیم.
۴. **فایل:** فایل‌ها در MinIO یا S3 می‌مانند و ماژول فقط لینک امضاشده می‌سازد.
۵. **آدرس محلی:** procedure به آدرس محلی وصل نمی‌شود، پس سرویس‌های بیرونی را با sandbox خودِ سرویس تست می‌کنیم.
۶. **پوش FCM:** امضای RS256 لازم دارد. در فاز ۷ یک امضاکنندهٔ JS خالص با BigInt ساختیم (`packages/publication/src/rsa.ts`) که داخل ماژول اجرا می‌شود و تست e2e امضای آن را بایت‌به‌بایت با Node مقایسه می‌کند. خود فراخوانی FCM بدون کلید واقعی تست نشده.
۷. **لایسنس:** برای هر برنامه فقط یک instance در production اجازه داریم. اگر بعداً بیش از یک ماشین لازم شد، برنامه را به چند دیتابیس تقسیم می‌کنیم.
۸. **تغییر schema:** فقط تغییرهای اضافه‌شونده خودکار هستند، پس از اول جدول‌ها را با دقت طراحی می‌کنیم.

## تصمیم‌ها

۱. **ریپو:** ریپوی اصلی فورکِ SpacetimeDB است و `upstream` آن ClockworkLabs است. همهٔ کد ما در پوشهٔ `platform/` است.
۲. **بازی‌ها:** هر بازی یک ریپوی جداست که از ریپوی اصلی فورک شده و `upstream` آن ریپوی اصلی است. هر بازی دیتابیس خودش را دارد. اولین بازی متاهوم است.
۳. **ترتیب فازها:** همین ترتیب تأیید شد.
